# TDJ Builder (Text Dynamics JSON)

Этот репозиторий — **генератор данных** для проекта **«Текст в динамике»**: попытки представить литературное произведение как творческий процесс через историю его изменений.

Ссылки на основной проект:

- Описание проекта: https://kultkod.github.io/text-dynamics.html  
- Визуализатор (демо): https://kultkod.github.io/text-dynamics/  
- Код визуализатора: https://github.com/zhenyacode/text-dynamics  

Проект исходит из идеи, что литературное произведение можно рассматривать не только как законченный текст, но и как процесс: последовательность рукописей, авторских правок, редакций и изданий. «Текст в динамике» позволяет перемещаться между такими состояниями текста и видеть изменения, которые превращают одну редакцию в другую.

---

## Что делает TDJ Builder

На входе:

- набор текстовых файлов (`txts/*.txt`) — разные редакции/состояния одного текста
- `manifest.yml` — описание версий и связей между ними (в т.ч. ветвления)

На выходе:

- `txts.json` — файл в формате **TDJ (Text Dynamics JSON)**: версии + переходы + операции правок

Плеер (frontend) уже **не считает diff на лету** — он просто открывает `txts.json` и визуализирует историю.

---

## Как это работает (pipeline)

1. `pipeline.py` читает `manifest.yml`
2. для каждой версии:
   - читает исходный текст из `txts/`
   - при необходимости разворачивает «фигурную разметку» правок (см. ниже)
3. Builder токенизирует версии (слова / пунктуация / границы абзацев)
4. Для каждого перехода `parent -> child` строится diff с помощью `difflib.SequenceMatcher`
5. Diff переводится в набор атомарных операций (удаления/вставки/замены) над плоским потоком токенов
6. Результат собирается в графовый TDJ и валидируется инвариантами
7. Записывается `txts.json`

---

## Формат данных: TDJ (кратко)

TDJ хранит текст **как плоский массив токенов** (`versions[].text`), а изменения — как операции над этим массивом.

- **Пробелы не хранятся** (визуализатор восстанавливает их при рендеринге по правилам).
- Граница абзаца хранится как **специальный токен** `meta.para` (по умолчанию `"\n\n"`).

### Графовый режим (используется здесь)

```json
{
  "meta": { "...": "..." },
  "versions": [
    { "id": "v1", "text": ["..."] },
    { "id": "v2", "text": ["..."] }
  ],
  "edges": [
    {
      "from": "v1",
      "to": "v2",
      "ops": [
        { "i": 10, "d": 1 },
        { "i": 10, "v": ["новое"] }
      ]
    }
  ]
}
```

Инвариант для каждого ребра:

> применение `edge.ops` к `versions[edge.from].text` даёт ровно `versions[edge.to].text`

Операция:

- `{ "i": N, "d": K }` — удалить K токенов с позиции N
- `{ "i": N, "v": [...] }` — вставить токены в позицию N
- `{ "i": N, "d": K, "v": [...] }` — замена
- `{ "i": N, "c": "..." }` — комментарий (не меняет текст)

Применение (как ожидается в плеере):

```js
function applyOp(tokens, o) {
  if (o.d == null && o.v == null) return;
  tokens.splice(o.i, o.d ?? 0, ...(o.v ?? []));
}
```

Полная спецификация TDJ — в документации основного проекта (см. ссылки выше).

## Разметка правок внутри одной рукописи (extractor)

Чтобы не хранить два почти одинаковых файла (до правки и после), Builder поддерживает «фигурную разметку» прямо в исходном тексте:

- `{+ins}` — вставка (появляется только в revised-слое)
- `{-del}` — удаление (остаётся только в base-слое)
- `{-old|+new}` — замена

`extractor.py` превращает такой текст в один или два снапшота: `base` и (если есть правки) `revised`. В `manifest.yml` можно указать, какой слой брать для конкретной версии: `layer: base|revised`.

Ограничения разметки:
- без вложенных `{...{...}...}`
- правка **не может пересекать границу абзаца**
- поддерживается только два слоя (base/revised)

## Структура репозитория

- `pipeline.py` — главный запуск: читает манифест + тексты → пишет `txts.json`
- `manifest.yml` — конфигурация версий и связей
- `txts/` — входные `.txt`
- `extractor.py` — разворачивает фигурную разметку в base/revised
- `diff_ops.py` — токенизация и сборка ops через `SequenceMatcher`
- `builder.py` — сборка графового TDJ + проверка инварианта
- `txts.json` — выходной файл (генерируется)
- `debugger.ipynb` — отладка/эксперименты (опционально)

python pipeline.py

## Важные допущения и ограничения (по смыслу проекта)

- Порядок правок в плеере **синтетический**: мы знаем два состояния текста, но не знаем реальную последовательность работы между ними.
- Результат зависит от токенизации и diff: иногда автоматический diff может «странно» интерпретировать изменения.
- Перемещения не выделяются отдельно: перенос = delete + insert.
- Внутри одной рукописи Builder пока различает только два слоя правок (base/revised).
- На больших текстах подход пока экспериментальный (производительность/удобство не гарантированы).

## Зачем всё это

Проект «Текст в динамике» пытается сделать эволюцию художественного текста видимой: показать версии, ветвления, переходы и конкретные изменения прямо в тексте.  
Этот репозиторий — **backend-подготовка данных** для такого плеера: из исходных текстов и связей между ними он собирает единый файл TDJ, который затем использует визуализатор.
