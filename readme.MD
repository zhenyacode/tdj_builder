# TDJ Builder (Text Dynamics JSON Builder)

**TDJ Builder** — инструмент для текстологов и Digital Humanities исследователей, который превращает разрозненные редакции литературного произведения и рукописные слои правок в единый граф версий формата TDJ. Полученный файл используется интерактивным веб-визуализатором («плеером текста») для пошаговой демонстрации того, как один вариант текста превращался в другой.

* 📖 **Статья о концепции:** [«Эволюция художественного текста или как подружить Гоголя и Git»](#) *(ссылка на публикацию)*
* 🎭 **Веб-визуализатор:** [kultkod.xyz/text-dynamics](https://kultkod.xyz/text-dynamics/)
* 🖥️ **Репозиторий визуализатора:** [kultkod/text-dynamics](https://github.com/kultkod/text-dynamics/)


## Быстрый запуск

В репозитории уже есть готовый пример — история редакций фрагмента комедии Н. В. Гоголя «Ревизор» (действие III, явление 6). Вы можете сразу собрать TDJ-файл на основе этих текстов.

**Требования:** Python 3.10 или новее.

**1. Скачайте репозиторий** с GitHub и откройте его папку в терминале. Если у вас установлен Git, это можно сделать командами:

```bash
git clone https://github.com/zhenyacode/tdj_builder.git
cd tdj_builder
```

**2. Установите зависимости:**

```bash
pip install -r requirements.txt
```

**3. Запустите сборщик:**

```bash
python pipeline.py
```

Скрипт прочитает тексты из папки `txts/`, загрузит описание версий из `manifest.yml`, вычислит различия между редакциями и соберёт граф истории текста.

**Результат:** файл `tdj-text.json` в корневой папке проекта. Он готов для загрузки в [веб-визуализатор](https://kultkod.xyz/text-dynamics/).


## Как собрать свой проект

Если вы хотите визуализировать историю другого произведения, выполните следующие шаги:

### Шаг 1. Подготовьте тексты

1. Удалите файлы с «Ревизором» из папки `txts/`.
2. Положите туда свои файлы в формате `.txt` (в кодировке UTF-8).
3. Каждый файл — это отдельная редакция, копия или публикация.

### Шаг 2. Разметьте правки внутри рукописи (опционально)

Если рукопись содержит правки автора прямо поверх строк (зачёркивания, вставки на полях), вы можете зафиксировать оба состояния в **одном файле** с помощью специального синтаксиса:

* `{+текст}` — вставка (автор добавил слова поверх строки).
* `{-текст}` — удаление (автор вычеркнул фрагмент).
* `{-было|+стало}` — замена одного фрагмента на другой.

**Правила разметки:**
* Фигурная разметка **не может пересекать границы абзаца** (пустые строки). Правка должна начинаться и заканчиваться внутри одного абзаца.
* Вложенные конструкции не поддерживаются (нельзя писать `{{+...}}`).

*Пример:*

```text
Я {-живу|+пребываю} в Петербурге. Мой дом на углу {+Невского} проспекта.
```

Скрипт автоматически создаст из такого файла два независимых текстовых слоя: `base` (текст до правки) и `revised` (текст после неё). Соответственно, в общей карте версий это будет две разных версии, `base` как исходная и `revised` как целевая.

**Если вы используете разметку внутри рукописи, важно указать корректную информацию в manifest.yml на следующем шаге (для каждого слоя надо будет создать отдельный блок в versions, который будет ссылаться на один и тот же файл, но будет иметь разные id и layer -- соответственно base и revised)**


### Шаг 3. Настройте manifest.yml

Файл `manifest.yml` описывает метаданные проекта, список редакций и связи между ними (граф эволюции).

Замените содержимое `manifest.yml` своими данными:

```yaml
meta:
  work: "Название произведения"
  part: "Глава, том или фрагмент"
  src: "Основной источник текстов / издание"
  note: "Пояснение для читателя (можно оставить пустым)"

versions:
  # Начальная версия (корень графа, без parent)
  - id: v1
    file: "1_черновик.txt"
    layer: base                     # нижний слой текста (до правок)
    title: "Черновой автограф"
    date_raw: "осень 1835"          # дата для отображения в интерфейсе
    date_tech: "1835-10-01"         # техническая дата (ГГГГ-ММ-ДД) для хронологии
    src: "РГАЛИ, ф. 123, оп. 1, ед. хр. 45"

  # Слой внутренних правок того же файла
  - id: v1_revised
    file: "1_черновик.txt"
    layer: revised                  # верхний слой текста (после правок)
    parent: v1                      # указывает на родительскую версию
    title: "Черновик с правками"
    date_raw: "ноябрь 1835"
    date_tech: "1835-11-15"
    src: "Тот же лист, слой правок"

  # Новая редакция в отдельном файле
  - id: v2
    file: "2_беловая_копия.txt"
    parent: v1_revised              # переход из слоя v1_revised в v2
    title: "Беловой автограф"
    date_raw: "1836"
    date_tech: "1836-01-01"
    src: "Издание 1836 года"
```

**Основные поля:**

* `id` — уникальный идентификатор версии (например, `v1`, `draft`, `p1836`).
* `file` — точное имя файла в папке `txts/`.
* `title` — название версии.
* `date_raw` — дата для отображения в интерфейсе (например, «осень 1835»).
* `date_tech` — дата в формате ГГГГ-ММ-ДД (нужна визуализатору для хронологии).
* `src` — источник конкретной версии.
* `note` — дополнительный комментарий (необязательно).
* `parent` — ID версии, из которой происходит текущая. Для начальной версии поле не указывается. Если несколько версий имеют одного родителя, граф разветвляется.
* `layer` — слой текста: `base` (до правок) или `revised` (после правок). Если поле не указано, используется `base`.

Обязательные поля каждой версии: `id`, `file`, `title`, `date_raw`, `date_tech`, `src`.

В секции `meta` обязательны все четыре поля: `work`, `part`, `src`, `note`. Поле `note` можно оставить пустым (`note: ""`).

### Шаг 4. Запустите сборщик

Запустите команду:

```bash
python pipeline.py
```

Сборщик автоматически:

1. Проверит целостность структуры (наличие файлов, отсутствие циклов и дубликатов ID).
2. Развернёт слои правок.
3. Рассчитает пошаговые переходы (diff) между связанными версиями.
4. Проверит инвариант: применение вычисленных правок к родительской версии должно давать точный текст дочерней версии.
5. Сгенерирует свежий `tdj-text.json`.

При повторном запуске существующий файл `tdj-text.json` будет перезаписан.


## Что делать с tdj-text.json?

Полученный файл `tdj-text.json` содержит граф версий вашего текста: сами редакции, связи между ними и последовательности правок для каждого перехода.

Чтобы увидеть результат:

1. Откройте [онлайн-визуализатор](https://kultkod.xyz/text-dynamics/).
2. Нажмите кнопку **загрузки файла** (значок со стрелкой вверх ⬆) в панели управления, слева от шестерёнки.
3. Выберите созданный вами файл `tdj-text.json`.

Визуализатор загрузит ваш проект. Теперь можно переключаться между редакциями на карте версий, пошагово просматривать вставки и удаления, перемещаться по истории текста с помощью слайдера или стрелок.

**Исходный код визуализатора:** [github.com/kultkod/text-dynamics](https://github.com/kultkod/text-dynamics/).


## Ограничения и особенности

TDJ Builder — экспериментальный исследовательский инструмент. Его модель упрощает реальную историю текста. Вот несколько известных ограничений:

* **Порядок правок синтетический.** Плеер показывает изменения последовательно, сверху вниз, но это не означает, что автор вносил их именно в таком порядке.
* **Результат зависит от токенизации и алгоритма сравнения.** То, как текст разбит на токены и как алгоритм `SequenceMatcher` сопоставил версии, определяет, какие правки увидит читатель. Иногда автоматический diff может интерпретировать изменения неудачно; возможности ручной корректировки пока нет.
* **Перемещения не выделяются отдельно.** Если фрагмент текста был перенесён, плеер покажет удаление в одном месте и вставку в другом.
* **Внутри одной рукописи поддерживаются только два слоя.** Разметка позволяет восстановить текст до и после исправлений. Для более сложной истории правок потребуется расширение модели.
* **Демонстрация «Ревизора» упрощена.** Использован ограниченный набор редакций по академическому изданию. Финальная версия в плеере — редакторский свод 1951 года на основе редакции 1842 года.
* **Работа с большими текстами пока не проверена.** На фрагменте «Ревизора» инструмент работает, но при обработке целой книги могут возникнуть проблемы с производительностью и удобством визуализации.
